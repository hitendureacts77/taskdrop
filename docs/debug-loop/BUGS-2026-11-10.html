B34A distance search drops nearby tasks: it keeps the newest 20 first, then filters by distance

Highsearch and maps (charter B)server
What you see
Search with a radius (e.g. 5 km) returns only those of the 20 newest open tasks anywhere that happen to be near you. With 190 open requests on staging now, most tasks around Kondapur never show in a radius search; it can even return "no results" while dozens are 2 km away.
Why
supabase/functions/api/reads.ts searchTasks (lines 149–178): .limit(limit(a)) runs in SQL, then the distance filter runs on that page. Same pattern, larger caps: tasksNear (newest 200), workersNear (300 most recently seen), recommendedTasks (newest 60).
Fix
When near is given, pre-filter in SQL with a bounding box (loc_lat between lat±r/111, loc_lng between lng±r/(111·cos lat)), then sort by distance and cap. Do the same box in tasksNear and workersNear. Keep inputs and response shape (rule 2). Add an api test: 25 far-away newer tasks + 1 near older task → the near one is returned.
Check
On taskdrop.in, Search → 5 km around Kondapur: expect 20 results, all within 5 km (staging has 76 open requests in that box).

B3813 older tasks still publish their exact pin (5 are still open or locked)

Mediumprivacydata
What you see
Staging rows whose public tasks.loc_lat/loc_lng have 4 decimals (~10 m) and no task_private row. Created 13 Sep – 31 Oct, around Kondapur. Everyone else's are rounded to 2 decimals (migration 074).
Why
They were written with triggers off (test scripts that use session_replication_role = replica), so the 074 rounding never ran. test_data.sql does the rounding by hand at its end; the other scripts do not.
Fix
One-off backfill (same SQL as the end of supabase/seed/test_data.sql: copy exact spot to task_private, round the public one). Then make scripts/two-person-test.mjs and friends round too, or add a nightly check that counts unrounded rows. Ask before running on staging.
Check
select count(*) from tasks where loc_lat <> round(loc_lat::numeric,2)::float8 returns 0.
