## Findings

### S2-1 · Posting and sending offers do not require a passed 18+ check
- Level: High · Area: tasks / bids insert rules, `handle_new_user` · Class: Backend · Where: all
- Steps: sign up a new number, stop before the date-of-birth step (or never pass it), then call `createTask` / `placeBid` through the api, or `POST /rest/v1/tasks` / `/rest/v1/bids` with the user token.
- Current: `public.handle_new_user()` gives every new account both `poster` and `worker` roles at sign-up. The insert rules only ask for the role: `tasks_insert_own` = `poster_id = auth.uid() AND private.has_role(uid,'poster')`; `bids_insert_own` = `worker_id = auth.uid() AND has_role(uid,'worker') AND task_open_for_bid(...)`. The only age trigger is `profiles_require_age_check`, which fires on `onboarded_at` only. No age test in the api either (`grep age_checks supabase/functions/api` hits only a read at `reads.ts:701`). Live: 35 profiles with no passed age check, 8 of them never onboarded; 17 tasks and 15 offers come from accounts without a passed check; 4 tasks from accounts that never finished setup.
- Expected: AGENTS.md "Users must be 18+": the server refuses to post, send an offer, accept a hire or start work until the person has a passed age check.
- Proof: `select ... from user_roles r left join age_checks a` → poster 204 users / 35 with no check; policy text from `pg_policy` for `tasks_insert_own`, `bids_insert_own`; `prosrc` of `handle_new_user`, `require_age_check_to_onboard`.
- Cause (if known): age gate is tied to "finish setup", while roles that unlock posting and offering are granted at sign-up. Related but wider than B39 (8 old accounts).

### S2-2 · Any signed-in person can read every profile's "private" fields straight from the database
- Level: Medium · Area: `profiles` read rule · Class: Backend · Where: all
- Steps: with any user token, `GET /rest/v1/profiles?select=id,earn_goal,referral_code,weekly_goal_minor,sessions_revoked_at,sessions_keep_session,payout_upi`.
- Current: `profiles_select_all` is `USING (true)` and `authenticated` holds table-wide SELECT, so every column of every profile is readable. `columns.ts:31-33` marks `payout_upi, sessions_revoked_at, sessions_keep_session, weekly_goal_minor, referral_code, earn_goal` as "Private - the owner only", and migration 179 says earn_goal is "owner-only", but that holds only inside the api. Edge logs show the Data API is live (`/rest/v1/profiles` 4,098 calls in 24 h), so the shortcut is open. Live data today: 185 referral codes; earn_goal and payout_upi are still empty.
- Expected: owner-only columns readable only by the owner (column grants, or move them to `profile_private` like other private data).
- Proof: `information_schema.column_privileges` (authenticated SELECT on all 29 profile columns); `pg_policy` profiles_select_all; `supabase/functions/api/columns.ts:4-5` comment ("every signed-in person can read every column"); migration `20261116100000_179_worker_earn_goal.sql:12-13`.
- Cause (if known): row rules guard rows, not columns; the api's fixed column lists are the only guard.

### S2-3 · "Parties only" money and hiring fields of every open task are readable by anyone signed in
- Level: Medium · Area: `tasks` read rule · Class: Backend · Where: all
- Steps: any user token: `GET /rest/v1/tasks?status=eq.OPEN&select=id,funded_minor,funded_credits_minor,funding_payment_id,funded_via,preferred_worker_id,wallet_refunded_at`.
- Current: `tasks_select_visible` lets everyone read OPEN tasks and `authenticated` has SELECT on every tasks column, including `TASK_PARTIES_ONLY` (`columns.ts:49-52`: funded_minor, funded_credits_minor, funded_via, funding_payment_id, locked_minor, locked_bid_id, payout_mode, wallet_refunded_at, preferred_worker_id). `redactTask` hides them only in api answers. Also, a losing bidder keeps row access after the hire (`user_bid_on_task`) and can read `locked_minor` (the winning price) directly.
- Expected: the server keeps parties-only fields from non-parties, as the api intends.
- Proof: `column_privileges` for tasks (54 columns, authenticated); policy `tasks_select_visible` = `status='OPEN' OR poster OR admin OR user_bid_on_task OR user_assigned_task`.

### S2-4 · A worker can replace or delete proof-of-work files after handing them in, even during a dispute
- Level: Medium · Area: storage bucket `task-media` rules · Class: Backend · Where: all
- Steps: worker uploads proof photo `<worker-id>/proof.jpg`, calls `submitProof` and `mark_work_done`; poster reports a problem (`open_dispute`); worker then `PUT`s a different file to the same path (upsert) or deletes it with the storage API.
- Current: storage policies "task media: owner replaces" (UPDATE) and "task media: owner deletes" (DELETE) allow any change to any object whose first folder is the caller's id, with no check that the file is referenced by a `task_proofs` row, a sent chat message or a task under dispute. Proof and chat evidence that staff use to decide a dispute can be swapped or removed by the person it is about.
- Expected: files referenced by a handed-in proof (and chat media) are frozen once sent; at least frozen while the task is WORK_DONE / REVISION_REQUESTED / DISPUTED.
- Proof: `pg_policy` on `storage.objects`: `task media: owner replaces` (w) and `task media: owner deletes` (d) = `bucket_id='task-media' AND foldername(name)[1] = auth.uid()`; `private.guard_media_owner_path` makes proof paths live in the worker's own folder.

### S2-5 · A poster can send work back for changes forever; "changes requested" has no timer, so the 3-day auto-approve never comes
- Level: Medium · Area: `request_revision`, `auto_complete_due` · Class: Backend · Where: all
- Steps: worker marks done; poster calls `request_revision` (no limit); worker marks done again; repeat. Or poster asks once and then goes silent.
- Current: `request_revision` sets `auto_complete_at = null`; `private.auto_complete_due()` only picks `status = 'WORK_DONE'`. A REVISION_REQUESTED task never auto-completes and the worker's money is held until the worker opens a dispute. Live: 4 tasks in REVISION_REQUESTED, all untouched for more than 3 days (oldest 31 Oct).
- Expected: AGENTS.md "poster has 3 days to approve or report, otherwise auto-complete": a cap on rounds and/or a deadline for the revision step.
- Proof: `prosrc` of `request_revision` and `private.auto_complete_due`; `select status, count(*) filter (where updated_at < now()-interval '3 days') from tasks` → REVISION_REQUESTED 4/4 stale.
- Note: listed in LEDGER "Questions for the owner" (round 3) without an id; repeated here because it is a server rule gap with live stale rows.

### S2-6 · The 5% cancel fine is paid straight into the worker's spendable balance: no 7-day clearing, no commission, no ledger row
- Level: Medium (rule gap only; payments not exercised) · Area: `cancel_task` (poster path) · Class: Backend · Where: all
- Steps: poster cancels a funded task in TASK_STARTED / OVERDUE.
- Current: `cancel_task` does `update wallets set balance_minor = balance_minor + v_fine` for the worker. Normal earnings go to `clearing_minor` and clear after `clearing_period_days` (7) via `settle_cleared_earnings`, minus `worker_commission_pct`. The fine skips both and writes no `wallet_adjustments` / `platform_ledger` row, so the reconcile cannot match it to a source. The poster refund (`private.refund_wallet_on_cancel`) also writes straight to `balance_minor`. The fine also applies in OVERDUE, i.e. when the worker is the one who is late (comment in `open_dispute` admits this).
- Expected: the product rule says earnings clear after 7 days; the fine is earnings for the worker. Owner to decide whether the fine clears and pays commission.
- Proof: `prosrc` of `public.cancel_task` (poster branch), `private.refund_wallet_on_cancel`, `confirm_release` (uses `clearing_minor`).

### S2-7 · Reviews have no length limit and no contact filter, and are public
- Level: Low · Area: `submit_review`, `reviews` table · Class: Backend · Where: all
- Steps: call `submit_review(task, 5, '<100 KB text with a phone number>')` on a finished task.
- Current: `reviews` has only `reviews_rating_check`; `submit_review` only trims the comment. Questions and answers block phone numbers, emails and links (`private.question_has_contact`), and feedback comments do too, but reviews (readable by everyone, `reviews_select_all USING true`) do not.
- Expected: a length cap (e.g. 1000) and the same contact filter as questions.
- Proof: `pg_constraint` for reviews (rating only); `prosrc` of `submit_review`.

### S2-8 · A task's photo stays downloadable after staff hide the task
- Level: Low · Area: `private.can_read_task_media` · Class: Backend · Where: all
- Current: the task-photo branches allow any signed-in person to read `t.media_path` when `t.status = 'OPEN'`, with no `private.task_is_hidden(t.id)` check (the proof-photo branch has one). Hidden (moderated) open tasks disappear from lists but their media is still served to anyone who has the path (it was in earlier list answers and caches).
- Expected: hidden tasks' media readable only by the poster, the hired worker and staff.
- Proof: `prosrc` of `private.can_read_task_media` (task branches vs the photos_public branch).

### S2-10 · A poster can change an open task's title, description, price and place after offers came in; bidders are not told
- Level: Medium · Area: `tasks_update_own_while_open`, `on_task_changed` · Class: Backend · Where: all
- Steps: worker sends an offer at Rs 500 for "carry one chair"; poster edits the task (api or `PATCH /rest/v1/tasks`) to "carry a sofa up 4 floors"; poster hires with `lock_bid`.
- Current: the update rule is `poster_id = auth.uid() AND status = 'OPEN'`; column grants allow `title, description, benchmark_minor, loc_lat, loc_lng, loc_label, due_at, time_limit_minutes, milestones, skills ...`. Nothing checks whether offers exist, nothing flags them, and `private.on_task_changed` sends nothing on an edit (it reacts only to status and funding changes). The hired worker is bound to a price for a different job.
- Expected: once an offer exists, either lock the scope fields or mark offers "task changed" and notify bidders so they can re-price.
- Proof: `pg_policy` tasks_update_own_while_open; `column_privileges` UPDATE on tasks; `prosrc` of `private.on_task_changed`.

### S2-11 · Bidders on an open task are not told when the poster cancels it
- Level: Low · Area: `on_task_changed` (CANCELLED branch) · Class: Backend · Where: all
- Current: on CANCELLED it notifies `v_closer` (the live or last worker, only when the old status was not OPEN) and the poster. Workers who only sent offers on an OPEN task get no notice; their offers stay on a cancelled task.
- Expected: a short "this task was cancelled" notice to every open bidder.
- Proof: `prosrc` of `private.on_task_changed` (`v_closer := coalesce(v_live, case when old.status <> 'OPEN' then ... end)`).

### S2-12 · No database check on task title or description length or emptiness
- Level: Low · Area: `tasks` constraints · Class: Backend · Where: all
- Current: `title` and `description` are only NOT NULL; no length/blank check (bids, messages, questions, feedback all have one). The table is writable directly through `POST /rest/v1/tasks` (column grant + `tasks_insert_own`), so a blank or 1 MB title can be posted around the api's Zod limits and would show on everyone's Home. Live data is clean today (max title 100, max description 461, 0 blank).
- Expected: CHECK constraints matching `packages/schemas` limits.
- Proof: `pg_constraint` list for tasks; `information_schema.columns` (NOT NULL only).

### S2-13 · A person can mark themselves "Active now" forever by writing `live_until` / `last_seen_at` directly
- Level: Low · Area: `profiles` column grants, `guard_profile_columns` · Class: Backend · Where: all
- Steps: `PATCH /rest/v1/profiles?id=eq.<me>` with `last_seen_at` and `live_until` = 2099-01-01.
- Current: `authenticated` may UPDATE both columns; `private.guard_profile_columns` protects only ratings, referral code, id and created_at. Presence is meant to be automatic (AGENTS.md, heartbeat every minute); helper lists filter/sort on `last_seen_at` (`supabase/functions/api/reads.ts:527`), so a future time keeps someone "active" and on top. Live: 0 rows do this today.
- Expected: the server clamps both to `now()`, or sets them only through a heartbeat RPC.
- Proof: `column_privileges` UPDATE on profiles; `prosrc` of `guard_profile_columns`.

### S2-14 · Offer delete rule says "you may delete your own offer", the trigger says "never"
- Level: Info · Area: `bids` · Class: Backend · Where: all
- Current: policy `bids_delete_own` (`worker_id = auth.uid() AND is_locked = false`) plus a table DELETE grant, but trigger `bids_keep_sent` refuses every app delete ("An offer cannot be taken back"). Not a hole (the trigger wins), but the dead policy and grant mislead readers and security tests. Cancelling an offer is impossible by design; editing is allowed while OPEN (`bids_edit_while_open`).
- Proof: `pg_policy` bids_delete_own; `pg_trigger` bids_keep_sent.

### S2-15 · 53 row rules call `private.is_admin()` per row instead of once per query
- Level: Low (performance) · Area: RLS policies · Class: Backend · Where: all
- Current: 53 of 119 policies use bare `private.is_admin()` (e.g. `bids_select_participants`, `tasks_select_visible`, `tasks_hide_*`, `messages_hide_moderated`, `reviews_hide_moderated`), so it runs (reading `user_roles`) for every row scanned. `user_roles` shows 328,762 sequential scans / 12.8 M rows read. Wrapping as `(select private.is_admin())` makes it once per query.
- Proof: count over `pg_policy` → 53 unwrapped; `pg_stat_user_tables` for user_roles.

### Checked and fine (no finding)
- Every SECURITY DEFINER function in `public`/`private` has a fixed `search_path`; the one with `search_path=pg_temp` (`private.assert_service_caller`) uses only built-ins.
- All 149 authenticated-callable SECURITY DEFINER functions: the ones with no `auth.uid()` or staff check in the body are read-only public helpers or guard themselves via `assert_feedback_member` / `assert_question_member`.
- RLS is on for every public table; no table grants anon anything; views `payments_unapplied` and `refunds_outstanding` are not readable by anon/authenticated.
- `wallets`, `payments`, `payouts`, `platform_ledger`, `wallet_adjustments` are read-only to users; `user_roles` / `settings` writes pass `is_admin` + `require_staff_permission` + MFA triggers.
- Lifecycle: `lock_bid` locks the task row and re-reads the offer price; double accept and accept-after-cancel are refused (status must be OPEN); `start_task` needs funding that covers the escrow and the current locked bid; `mark_work_done` needs a proof; `confirm_release` / `auto_complete_due` put the net (commission 10% from `settings`) into `clearing_minor` with a 7-day `clear_at`; `run_overdue_tasks` moves TASK_STARTED past `due_at` to OVERDUE; work already sent cannot be cancelled, only disputed.
- Counters: rating counts match reviews (0 drift), feedback vote counts match votes, no negative wallets, no duplicate offers per worker per task, no self-offers, no duplicate reviews. Outbox: 0 unsent.
- Task and profile pins are rounded to 2 decimals by triggers; exact pins live in `task_private` (parties only).
