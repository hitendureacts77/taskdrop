## Findings

### S6-1 · Keyboard Send / Enter has no busy guard on the number, birth and password boxes
- Level: Medium · Area: AccessScreen · Class: UI · Where: all
- Steps: type a valid 10-digit number, press the keyboard "Send" (or Enter on web) twice quickly. Same on the birth-date box (`BirthDateField onSubmit`) and the password box of the username sheet.
- Current: `onSubmitEditing` calls `sendCode()` / `confirmBirth()` / `passwordSignIn()` directly; none of them checks `busy` / `pwBusy` (only the buttons are disabled while busy). Two requests go out. The server refuses a second code inside 60 s, so the person is shown that refusal as an error toast although the first code was sent and the screen is on the code step.
- Expected: ignore a submit while a request is in flight.
- Proof: `AccessScreen.tsx:467` (`onSubmitEditing={() => void sendCode()}`), `:172-175` (`sendCode` checks only `numberReady`), `:201-218` (`confirmBirth`), `:304-308` (`passwordSignIn`), `:813`.
- Cause: guards live on the buttons, not in the handlers.

### S6-2 · A 10-digit number that does not start with 6-9 gives no explanation, and the keyboard "Send" says the wrong thing

- Cause: the rule and the message were written separately.

### S6-3 · Sign-in code step: "No code? Ask again in 0:60"
- Level: Low · Area: AccessScreen (code step) · Class: UI · Where: all
- Steps: request a code; look at the resend line in the first second.
- Current: `resendAt = Date.now()+60000`, then `setNow(Date.now())` a few ms later, so `Math.ceil((resendAt-now)/1000)` is 60 and the line reads `0:60` before it settles to `0:59`.
- Expected: `1:00` or start at `0:59`.
- Proof: `AccessScreen.tsx:158-159`, `:113`, `:743` (`0:${String(waitSec).padStart(2,'0')}` is also wrong for any value of 60).
- Cause: seconds formatted as `0:SS` with no minute part.

### S6-4 · Date of birth typed for one number is reused for a different number after "Change"
- Level: Medium · Area: AccessScreen (new-account step) · Class: UI · Where: all
- Steps: type new number A, enter a birth date, reach the code step; tap "Change", type a different new number B, tap "Text me a code".
- Current: `birth` (and `dob`) are never cleared by `editNumber`, so for B the birth question is skipped (`if (used === 'signup' && !birth)` is false) and A's birth date is recorded against B's new account.

- Proof: `AccessScreen.tsx:183` (`!birth`), `:321-325` (`editNumber` resets stage and otp only), `:247-253` (`recordBirthDate(birth)`).
- Cause: `birth` is not tied to the number it was given for. This weakens the age gate (rule: users must be 18+): the date on file for the second account was not given for it.

### S6-5 · A valid code followed by a failure after sign-in is reported as a wrong code, the code is cleared and the person is stuck on the code step

### S6-39 · Chat and post contact filter lets contact details through
- Level: Medium · Area: chat `findContactIssue`, server `sendMessage` (same patterns in `_shared/contacts.ts`) · Class: Both · Where: all
- Steps: in a chat before the work starts, send each text; each was run through `findContactIssue` from `apps/mobile/src/lib/mask.ts` (Node 22 on a copy of the file, 17 Nov). Result in brackets:

- Current: these send. A UPI id also moves the payment off TaskDrop, which is what the rule protects (AGENTS: contacts unlock when work starts; money held until approval).

- Proof: scratch run described above; `mask.ts:80-90` vs `:47` (mask has `insta`); the server copy `supabase/functions/_shared/contacts.ts:47,87`.

### S6-41 · Live chat can miss messages when the phone's clock is ahead of the server's
- Level: Medium · Area: ChatScreen live updates · Class: Both · Where: all
- Steps: set the phone clock a few minutes fast, open a chat, have the other person send a message.
- Current: `subscribeToMessages` starts its cursor at `new Date().toISOString()` (the phone's clock) and asks the server for messages `after` it. A message the server stamped earlier than that cursor is never returned, and the cursor only moves forward, so it stays missing until the chat is reopened.
- Expected: start the cursor from the newest loaded message (server time), not the device clock.
- Proof: `data/api.ts:279,286-288`, `ChatScreen.tsx:188-206`.
- Cause: device clock used as a server cursor.
