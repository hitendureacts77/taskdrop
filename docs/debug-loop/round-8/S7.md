## Findings

### S7-1 · Several staff changes leave no audit-log row at all
- Level: Medium · Area: audit log (H77-H80) · Class: Backend · Where: admin
- Steps: code path. Add, edit, pin, finish or delete a customer note; delete a tag; save or delete a segment; reply to or resolve a help request; mark alerts read.
- Current: none of these writes an `admin_audit_log` row. The audit triggers exist only on `payouts`, `wallet_adjustments`, `user_suspensions`, `user_roles`, `dispute_decisions`, `settings`, `crm_broadcasts` (`supabase/20261004123000_076_audit_throttle_live_notifications.sql:97-105`), `copyright_notices` (085) and `admin_staff` (089). The RPCs that log by hand (`admin_log_event`) cover warn, hide/unhide, category, owner assignment, follow-ups, leads, rules, promotions, cancel, feedback and tags, but not `crm_add_note`, `crm_update_note`, `crm_delete_note`, `crm_save_segment`, `crm_delete_segment`, `reply_support_ticket`, `resolve_support_ticket`. `public.crm_delete_tag` is `delete from public.crm_tags where id = p_tag;` with no log (`supabase/20261004100000_071_crm.sql:279-289`), so one click removes a tag from every person with no record of who did it.
- Expected: every staff write that changes data about a customer, or what staff or customers see, is in the audit log with the actor and the target.
- Proof: `lib/crm-actions.ts:33-150, 247-272`, `lib/actions.ts:309-337`, `lib/admin-config.ts:295-310` (the only audit groups the panel can show).
- Cause: audit is per-RPC or per-table-trigger, and these RPCs and tables were never added.

### S7-2 · Tag add and remove are logged in a second call whose failure is ignored
- Level: Low · Area: customer tags · Class: Backend · Where: admin
- Steps: code path. `assignTag`, `removeTag`.
- Current: the tag change is committed first (`crm_assign_tag`), then `admin_log_event` is awaited and its result is thrown away. If the second call fails (rate limit, network, a database error), the change stands with no audit row and the person sees "Tagged".
- Expected: the log write and the change happen together, or the failure is reported.
- Proof: `lib/crm-actions.ts:112-115` and `lib/crm-actions.ts:130-132` (`await call('admin_log_event', ...)` with no check of `.error`).
- Cause: non-atomic two-step write.

- Cause: the audit write sits in a render path that Next re-runs on refresh and revalidation.

### S7-5 · A backslash in the search box is not escaped, so "abc\" matches nothing
- Level: Low · Area: Jobs, People, Search, Payouts search · Class: Backend · Where: admin
- Steps: type `abc\` in the Jobs or People search.
- Current: `likeTerm` escapes `%` and `_` but not `\` (`lib/data/search.ts:228-230`). The stripped term keeps the backslash, so `abc\` becomes `%abc\%` and the trailing `\%` is read as a literal percent sign. A backslash in the middle (`a\b`) is read as an escape and matches "ab". - Expected: a backslash matches itself.
- Proof: `lib/data/search.ts:223-230`, used at `lib/data/tasks.ts:96-97` and `lib/data/users.ts:447-459`.
