# Round 8 · S1 · Server API code audit

Covered: a code read (no live browser, no SQL run) of `supabase/functions/api/` (index, ops, core, reads, writes, media, guest, repeat, http, publicMemo, columns and the tests), `supabase/functions/_shared/` (contacts, controls, rules, place, rateLimit, signInSwitches, sendCaps, forwardedFor), `places-search`, `phone-auth`, `password-auth`, `app-config`, `app-download` and the head of `inngest`, with the SQL behind each operation read where the server leans on it (RLS policies, triggers and functions in `supabase/migrations/`), and the app's caller (`apps/mobile/src/data/api.ts`, `lib/gateway.ts`, `lib/errors.ts`) for shapes and error handling. Razorpay and RazorpayX functions and money movement were not read. No width, theme or account applies (no live walk). Date: 16-17 Nov 2026. Every finding below was searched for in `LEDGER.md`, `ROUND-7.md` and `round-7/*.md` first.

### S1-1 · The 18+ rule is only checked when finishing setup; posting, offers, chat and hiring never check it
- Level: High · Area: age gate, every write · Class: Backend · Where: all
- Steps: sign up by phone (an account exists at once), skip the date-of-birth step (call the api directly, or any build that lets a not-onboarded account act), then call `createTask`, `placeBid`, `sendMessage`, `lockBid`.
- Current: all of them run. The only server checks of `age_checks.passed` are the onboarding trigger, City Hunt and the people map.
- Expected: every operation that involves other people or money refuses an account without a passed age check ("Users must be 18+", AGENTS.md product rules).
- Proof: `20261004190000_082_age_gate.sql:126-148` (trigger fires only `before update of onboarded_at`); `20260911045822_003_harden_functions.sql:51-55` (`tasks_insert_own`: `poster_id` and `has_role` only); `20260911061248_004_fix_rls_recursion.sql:53-58` (`bids_insert_own`: role and task open only); `age_checks` used elsewhere only in `158_city_hunt.sql:417`, `159_people_map.sql:96`, `160_people_map_everyone.sql:71,125,219`; `api/writes.ts:297` (`createTask`), `:404` (`placeBid`), `:473` (`sendMessage`) have no age or onboarded check.
- Cause (if known): the gate was written as "cannot finish setup", and the writes assume setup was finished. Related to B39 (old accounts without a check), which is about data, not the missing rule.

### S1-2 · The admin "sign-ups paused" switch is skipped by leaving out `mode` in phone sign-in
- Level: High · Area: phone-auth, admin switches · Class: Backend · Where: all
- Steps: with `signups_open` off in the admin, POST `phone-auth` `{action:"send", phone}` without `mode`, then `{action:"verify", phone, code}` without `mode`.
- Current: send checks only the "phone sign-in" switch unless `mode === "signup"`; verify always checks only the phone switch, and with no `mode` it takes the sign-up path and creates the account.
- Expected: a new account is refused while sign-ups are paused, whatever the request says about itself.
- Proof: `phone-auth/index.ts:240-243` (`body.action === "send" && body.mode === "signup" ? "signup" : "phone"`), `:462` (`wantsSignIn = body.mode === "signin"`), `:504-527` (creates the user when not sign-in); `_shared/signInSwitches.ts:26` (signup switch only for kind "signup").
- Cause (if known): the switch is keyed on what the client says it is doing, not on whether an account is about to be created. (Google sign-up also skips it, as the file says; that one is by design.)

### S1-3 · Phone numbers pass the contact filter with other separators, invisible characters or other digit sets
- Level: Medium · Area: contact filter for offers, chat before work starts, posts, bios · Class: Backend · Where: all
- Steps: send an offer message, a chat message on an OPEN task, a task description or a bio with: `98765/43210`, `98765,43210`, `98765_43210`, `9​8​7​6​5​4​3​2​1​0` (zero-width spaces, U+200B, between digits), `𝟗𝟖𝟕𝟔𝟓𝟒𝟑𝟐𝟏𝟎` (mathematical bold digits), `98765 four three two one zero` (digits mixed with fewer than eight number words), `ravi @ gmail . com`.
- Current: all of them are accepted (read from the regexes; not sent live).
- Expected: refused like `98765 43210` is.
- Proof: `_shared/contacts.ts:44` (phone pattern joins digits only with `\s - . ( )`; JS `\s` does not include U+200B); `:18` (`DIGIT_BLOCKS` stops at full-width U+FF10, so U+1D7CE digits are left as they are); `:29` (number words converted only in runs of 8 or more words); `:36-38` (email needs no spaces around `@`, or the words "at"/"dot", or brackets).
- Cause (if known): the patterns list the spelling tricks found so far; separators and digit sets outside the list fall through.

### S1-4 · UPI ids pass every contact filter
- Level: Medium · Area: contact filter (offers, chat, posts, bios, questions, board) · Class: Backend · Where: all
- Steps: put `ravi@okaxis` or `9876@ybl` in an offer, a chat message before work starts, a post or a bio.
- Current: accepted. A UPI id is a payment handle: both sides can settle off TaskDrop, which is the whole reason contacts are held back.
- Expected: refused like an email.
- Proof: `_shared/contacts.ts:36,85` (email needs a dot and a TLD after `@`); handle pattern `:46,88` needs a space or start before `@`; SQL `private.question_has_contact` and `feedback_has_contact` use the same TLD rule (`140_task_questions_and_nearby_pulse.sql:65`, `136_feedback_board.sql:124`). `9876@ybl` also slips the phone rule (4 digits).

### S1-5 · Public questions, answers and the Ideas board use a weaker contact check than the api
- Level: Medium · Area: task questions (public), feedback board (public) · Class: Backend · Where: all
- Steps: ask a question on any open task with `९८७६५४३२१०` (Devanagari digits), `nine eight seven six five four three two one zero`, `9️⃣8️⃣7️⃣...`, `whatsapp ravi_k`, `@ravi_fixes`, or `98765/43210`.
- Current: the SQL check only looks for an ASCII email, an ASCII 10-digit Indian number after removing ` ().-`, 10+ ASCII digits, and (questions only) a few link shapes. None of the above are caught. Questions and answers are readable by every signed-in person and by guests.
- Expected: the same rules as `_shared/contacts.ts` (digit normalisation, handles, chat apps), since these are the most public texts in the app.
- Proof: `20261102170000_140_task_questions_and_nearby_pulse.sql:59-68`; `20261102120000_136_feedback_board.sql:118-126`; `api/writes.ts:767-768` passes the text straight to SQL with no `refuseContacts`.

### S1-6 · Posts and chat before work starts allow "insta", and no filter catches bare web addresses
- Level: Medium · Area: contact filter · Class: Backend · Where: all
- Steps: post a task (or send a chat message on an OPEN task, or save a bio) with "DM me on insta ravi_k", or "see ravifixes.in", or "bit.ly/ravi".
- Current: `findContactIssue` (posts, bios, pre-start chat) has no "insta/instagram" word, while `maskContacts` (offers) does. Neither catches a bare domain without `http`/`www` (except a few named sites).
- Expected: one list of chat apps for every text; bare domains caught (the SQL question check already does it for .com/.in/.net and others).
- Proof: `_shared/contacts.ts:88` (`whats\s?app|telegram|snapchat|call me on|ping me on`) vs `:47` (`whats\s?app|insta(?:gram)?|telegram|...`); `:40-41,87` (links need `https?://`, `www.` or a named host).

### S1-9 · A chat message that starts with `::media::` skips the contact check

### S1-10 · Door numbers like "A-402", "H-12" or "12 MG Road" stay in the public area label

### S1-11 · A profile picture may be any outside web address
