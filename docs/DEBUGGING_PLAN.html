The debug loop

A repeating round of find → fix → recheck. Each round looks for new bugs, fixes the worst ones, proves the old fixes still hold, and tells you what is still open. Rounds repeat until the number of new bugs settles near zero.

1. The loop at a glance

Eight steps make one round. Step 8 decides: go round again, or stop because the app has settled. The ledger file is the memory between rounds, so nothing found is ever lost and nothing fixed is ever assumed.

2. How many rounds, and when to stop

A fixed number of rounds would either stop too early or waste time. So the loop has a floor, a ceiling and a clear stop test.

Floor: 3 rounds

Even a quiet first round is not proof. Three rounds means every main area of the app (posting, earning, money) has had its own focused look.

Ceiling: 8 rounds

If round 8 still finds a Critical or High bug, more rounds will not help. The loop stops and does a hot-spot review instead (see below).

Rhythm: every 2–3 days

Long enough for fixes to reach staging and for you to answer "fix" or "accept". During the 14-day tester window, every 3–4 days, matched to the tester rounds (3.4).

The stop test (all must be true)

#RuleWhy
S1Two rounds in a row found no new Critical or High bugOne quiet round can be luck; two is a trend
S2No Critical or High bug is openThe same rule as the hunt (2.14) and Gate 3
S3The last round found 2 or fewer new bugs, and fewer than the round beforeThe find rate is falling, not just bouncing
S4Every bug marked fixed is rechecked on staging (none stuck at "fixed, not rechecked")"If you didn't fix it, it ain't fixed" (Agans' rule 9)
S5Every automatic check passed in both runs of the last two rounds (no flaky test)A test that passes only sometimes hides real bugs
S6The golden path passed on the website, the Android app and the adminPost → offer → pay → work → approve → review → withdraw is the business
S7Every open Medium and Low has your answer: fix, accept, or after launchNothing open is forgotten; it is either queued or accepted on purpose
Hot-spot review (the circuit breaker). If round 8 is reached without settling, or one area (for example the map, or money) produces new bugs three rounds running, Claude stops looking for more bugs there. Instead it lists every bug from that area side by side, looks for the shared cause (one weak function, one missing test layer, one screen built in a hurry), and proposes one deeper fix for your yes. Then the loop starts again at round 1 for that area.

3. One round, step by step

Every round does the same eight steps in the same order. The result of each step is written down before the next starts.

  1. Pin: fix the target

    Claude · 5 minutes

    Write down exactly what is being tested: the commit of redesigned-2.0, what is live on staging (taskdrop.in, the admin, the server functions), and the Android app build and update group on your phone. Every bug found this round belongs to this snapshot.

    Why: a bug report that does not say which version it is from cannot be rechecked. Also lets Claude say "this worked in round 2, broke in round 3" and search only the changes in between.

  2. Collect: read the signals since the last round

    Claude · 20 minutes

    • Sentry (app, server functions, admin): new issues, and old ones that came back
    • Vercel runtime errors and Supabase logs and advisor warnings
    • People: the Ideas & feedback board, Help & support messages, testers' reports (3.4), anything you said in chat
    • Usage: PostHog drop-offs and rage clicks (once 3.3c is on), Uptime Robot
    • The ledger: bugs fixed last round that still need a recheck

    Gives: the "reported" list. Each item is checked by hand before it becomes a bug; a signal is not yet proof.

  3. Sweep: run every automatic check, twice

    Claude · 30–40 minutes, mostly waiting

    npm run check (typecheck, lint, unit tests), npm run test:contract, npm run test:db, npm run test:e2e (Playwright, including the monkey and break-it tests), npm run audit:gate, and the admin's typecheck, lint and test. Everything runs twice. The sweep also searches the code for any leftover [DBG- debug log (section 7, rung 5); one found is a bug of its own.

    Gives: red tests (real bugs or broken tests) and flaky tests (passed once, failed once). A flaky test is logged as a bug of its own.

  4. Explore: this round's charter, plus the golden path

    Claude, with you for the phone parts · 1–2 hours

    Each round has one charter from the deck in section 4: a focus area and a list of things to try on purpose (wrong order, double taps, back button, slow network, an empty list, a very long text). Claude uses the real website in Chrome and, when your phone is connected, the Android app. Every round also runs the golden path once from start to end, so a broken core never hides behind a narrow charter.

    Before each try, Claude clears the browser console, then reproduces, then copies every console line and failed network call at once, so the log holds only this bug. Each finding is classified on the spot: UI (looks or behaves wrong on screen, the data is right), Backend (sign-in, row-level security, storage, an Edge Function or a database function), or Both.

    Gives: new bugs, each with a class, steps, current and expected behaviour, and a screenshot or log as proof.

  5. Log & triage: one ledger entry per bug

    Claude · 15 minutes

    Each finding is first matched against the ledger: the same cause as an old bug means the old entry is reopened, not a new number. New bugs get the next number (from B33), a level and a status. Security holes keep their H numbers in the plan's Security section; the ledger links to them.

    Order of fixing: Critical → High → anything that blocks testing → Medium you said "fix" to → Low you said "fix" to. At most about 8 fixes a round, so a round stays short; the rest carry over and say how many rounds old they are.

  6. Fix: failing test first, then the cause

    Claude · most of the round

    Each bug follows the fix routine in section 6. Short branch per bug (or small group), pull request into redesigned-2.0, merged when every check is green. Critical and High are always fixed. Medium and Low wait for your "fix".

    Gives: merged pull requests, each bug marked fixed, not rechecked.

  7. Recheck: prove it on staging

    Claude · 20–30 minutes

    Once the fixes are live on staging, Claude repeats each bug's original steps there (not just on the computer), and runs the sweep once more to make sure no fix broke something else. Before saying a fix did not work, Claude hard-refreshes the page (Ctrl+F5); a sign-in mix-up is retried after clearing that site's cookies and stored data, so an old cached page is never mistaken for a failed fix. Fixes that need the Android app are rechecked after the next app update, which Claude asks you about first.

    Gives: verified or reopened for each fixed bug.

  8. Report: what is new, what is fixed, what is still open

    Claude writes it · you read it in 10–15 minutes

    The round report (section 8) goes in docs/debug-loop/ROUND-N.md; the ledger's round table gets one new line; task 2.19 in the ultimate plan gets a one-line status. Then the stop test: settled (stop, go weekly), go again (the next charter is named), or hot-spot review.

    Yours: reply "fix", "accept" or "after launch" to each Medium and Low in the "needs your answer" list.

5. The bug ledger

One file, docs/debug-loop/LEDGER.md, holds every bug the loop has ever seen. It is the answer to "what is new, and what is still not fixed" at any moment, and it is what lets every round start fresh from files instead of from memory.

The life of a bug

New→Confirmed→Fixing→Fixed, not rechecked→Verified→Closed

Side doors: Reopened (a recheck failed, or it came back later), Accepted (your "accept"), After launch (your choice, goes to Future scope), Cannot reproduce (tried three ways, kept for two rounds in case it returns), Duplicate of B... A Verified bug becomes Closed after one more round with no sign of it.

Levels (the same as tasks 2.7 and 2.14)

LevelMeansRule
CriticalMoney or private data at risk, or the app cannot be used at allFixed in this round, before anything else
HighA main step of the golden path fails, or wrong data is shown to someoneFixed in this round
MediumA feature is broken but there is a way around it; confusing or misleading screensYour "fix", "accept" or "after launch"
LowLooks wrong, rare, or fake-data onlyYour answer; fixed in batches

Level says how bad it is. Order (section 3, step 5) says what is fixed first. The two are kept apart on purpose: a Low bug that stops testers from testing goes before a Medium nobody reaches.

6. How one bug gets fixed (the fix routine)

Seven steps, the same for every bug. They come from the debugging books and talks in section 11, and from gstack's /qa loop, which this PC already has. How hard to dig for the cause is set by the ladder in section 7.

1. Make it fail on demand

Write down the exact steps that show the bug, every time, and say if it is UI, Backend or Both. If it cannot be made to fail, it cannot be proven fixed: it stays "Confirmed" and gets more logging, not a guess.

2. Write the failing test first

A unit, database, contract or Playwright test that fails because of this bug. Screens only Android can show get a written recheck step instead, and the report says so.

3. Look, then guess

Collect the evidence pack first (section 7, rung 2): screenshot, current and expected behaviour, a clean console log, and for Backend bugs the security rules in force. Then write one cause to test, try to prove it wrong, and write the result in the entry. Before changing code, write the cause and the smallest fix in one or two lines.

4. Cut the search in half

If it worked in an earlier round, compare the two pinned commits and halve the changes until one is left (git bisect). If one input triggers it, shrink the input until only the trigger is left.

5. Fix the cause, small

The smallest change that removes the cause, not the symptom. No new features while fixing (the freeze). Anything bigger becomes your question.

6. Green, then merge

The new test passes, the whole sweep passes, a pull request into redesigned-2.0, merged. A fix with a database migration waits for your yes first.

7. Recheck on staging

The original steps, on staging, after the fix is live. Only then "Verified". The test stays in the suite forever, so every later round rechecks it for free.

One bug at a time

Fixes are never stacked. One bug's fix is proven (its test passes, the sweep passes) before the next bug is touched, so when something breaks it is clear which change did it.

Restore, don't pile on patches

If two tries at a fix have failed, Claude stops patching. The branch goes back to the last good commit (the pinned one), and the bug is planned again as one whole fix from the evidence, instead of a third patch on top of two wrong ones.

Who does what

Opus works out hard causes; Sonnet helpers run sweeps, rechecks and collect the evidence packs (your model split, which also saves usage, as the lesson's "draft the prompt first" tip does). A fresh look by a second agent is used when a cause is still unclear after two tries.

Learn from the slow ones

A bug that needed three or more tries gets a short retro in its entry, and the lesson goes into docs/debug-loop/BUG_PROMPT.md (section 7, rung 6), so the next bug like it is found faster.

7. The dig-deeper ladder (how hard to look for the cause)

Most bugs are found on the first two rungs. A bug climbs one rung only when the rung below did not find the cause. The ledger entry says which rung it reached, so a round report shows which bugs were hard. This ladder comes from the Starter Story lesson on debugging (section 11), changed from the Lovable tool to how TaskDrop is built: Claude Code, Supabase, the api Edge Function, Chrome and your phone.

  1. Rung 1 · The quick try

    When the error already names the place

    A typecheck or lint error, a red Vercel build log, or a Sentry error whose stack points to one line of our code. Claude tries that one obvious fix and rechecks. If it does not work the first time, straight to rung 2: no second guess.

  2. Rung 2 · The precise bug report and the evidence pack

    Every bug that is not fixed on rung 1

    • Reproduce in a fresh browser tab (or the phone), with the console cleared first
    • Class: UI, Backend or Both
    • Screenshot of the exact element or state, and current vs expected in plain words
    • Console log and failed network calls, copied all at once right after reproducing
    • Backend or Both: the row-level security rules on the tables involved (read from pg_policies), the storage bucket's rules (on storage.objects) when files are involved, and the api Edge Function and Supabase logs for that minute

    Then: name the cause (for UI: overflow, clipping, layer order, width, state not refreshed; for Backend: which rule or check refuses or lets through), and the smallest fix, before changing code. For a Backend fix, the exact rule or SQL change and why it is still safe (least access) is written into the pull request; a new database migration still waits for your yes.

  3. Rung 3 · Restore and re-plan

    After two failed tries at a fix

    Back to the pinned commit, read the evidence again, write one whole plan for the fix. No third patch on top.

  4. Rung 4 · The diagnostic SQL script

    A Backend bug that is still unclear

    Claude writes docs/debug-loop/diagnostics/B<n>.sql: numbered steps (STEP 1 … STEP N), each with a comment saying how to read its result. Typical steps: who the database thinks the user is (auth.uid(), run as the fake person inside a transaction that is always rolled back); the target row and its owner; what the security rule allows for this person; whether the stored file exists at that path and who may touch it; and a read-only select that copies the filter of the failing action. Claude runs each step on staging, read-only, and saves the results as JSON next to the round report.

    Then: a short cause summary, the exact rule or SQL change, any code change with file and line, and how to test it.

  5. Rung 5 · Targeted debug logs

    The trail is still cold

    Claude adds a few log lines with one searchable prefix, for example [DBG-B41], on every step of the broken path: the button handler (what was pressed, which task, which user id), the call to the server (which api operation and its input), the Edge Function (each check it passes or fails, the outcome), and the database step (the filter used and how many rows it changed). Only these lines, no other noise. Reproduce, read the [DBG-B41] lines, find the exact break point, make the smallest fix.

    Rules: no phone number, email, secret or exact address in any log line (AGENTS.md rule 9; ids only). The debug lines are removed in the same pull request as the fix, and the sweep checks that no [DBG- line is left. An Edge Function with debug lines goes only to staging.

  6. Rung 6 · Retro and the bug template

    After any bug that needed three or more tries

    Claude writes three lines in the entry: why the first tries missed the cause, which evidence should have been collected first, and what a better first plan would have been. The lesson goes into docs/debug-loop/BUG_PROMPT.md, the standing template every round reads first: what to collect (phase 1), the cause checklist for UI, security rules, storage and Edge Functions (phase 2), one whole fix plan (phase 3), the test list (phase 4), and what not to do.

When you find a bug yourself

Send it in chat in this shape. Claude reads BUG_PROMPT.md, follows it, says the plan, then fixes it (Critical and High at once; Medium and Low go into the ledger for your "fix" or "accept").

8. Rules and safety

Where

  • Staging only. Never production, never the payment companies' live systems
  • Only the fake people (Asha, Ravi, Meera) and test accounts
  • Claude never types into a payment page

Asks you first

  • An app update to the testers' phones
  • A fix that adds a database migration (merging one applies it to staging)
  • Wiping or resetting test data, any key change

The freeze holds

  • The loop only fixes. A finding that is really a new idea goes to Future scope
  • A fix that needs a design change becomes your question with a sketch

Nothing quietly dropped

  • Every finding gets an entry, even "cannot reproduce"
  • Nothing is marked fixed without a recheck on staging
  • Anything Claude could not check (no phone, no money in the wallet) is named in the report

Habits between rounds too

  • Test after every finished task: whenever any build task ends, Claude opens what was just built and tries it straight away, not only in the next round
  • Evidence before code: screenshot, console log, security rules or a SQL check come first
  • One fix at a time, and restore, then retry instead of piling patches

Debug logs and SQL stay safe

  • Debug log lines carry ids only, never a phone, email, secret or exact address, and leave in the same pull request
  • Diagnostic SQL is read-only and always rolled back; any rule change is a migration that waits for your yes

10. Where these ideas come from

Each source gave one part of the loop. Links open the original.

Book and site

David Agans, "Debugging: The 9 Indispensable Rules"

The fix routine: make it fail, quit thinking and look, divide and conquer, change one thing at a time, keep an audit trail (the ledger), get a fresh view, and "if you didn't fix it, it ain't fixed" (the recheck step and rule S4).

YouTube talk

Stuart Halloway, "Debugging with the Scientific Method" (Clojure/conj 2015)

Step 3 of the fix routine: one stated guess at a time, try to prove it wrong, shrink the search space, and write every step down. That is why each ledger entry has a "Cause" line.

GitHub repo and YouTube

Andreas Zeller, "The Debugging Book" (uds-se/debuggingbook) · intro video

Step 4 of the fix routine: shrink a failing input to the smallest one that still fails, and find the change that broke it automatically. The pinned commit per round makes this possible.

GitHub repo

garrytan/gstack, the /qa skill

The test → fix → verify shape of a round, the "write a failing regression test before the repair" rule, a report per run, and a report-only mode. Already installed on this PC.

GitHub repo and YouTube

Geoffrey Huntley, the "Ralph" loop (ghuntley/how-to-ralph-wiggum) · video

The idea of running the same instruction again and again with the state kept in files, not in the chat, until a stop rule is met. That is why one sentence, "start debug round", is enough and why the ledger is a file.

Docs and GitHub

Playwright Test Agents (planner, generator, healer)

Explore → write the test → repair a broken test as three separate jobs. TaskDrop's e2e tests already use Playwright, so new regression tests go there.

GitHub repo

mobile-dev-inc/maestro · Expo's guide

The optional Android golden-path flow in section 10.

Zine and blog

Julia Evans, "A debugging manifesto" and "The Pocket Guide to Debugging"

The attitude behind the rules: every bug has a logical reason, question your own guesses, and take the "cannot reproduce" ones seriously instead of closing them.

GitHub triage guides

Traefik's issue triage guide · Eclipse Che: keep severity and priority apart

Triage right after finding, match against what is already known before giving a new number, and keep "how bad" (level) apart from "what first" (order).

Guides

How to run a bug bash: charters, time boxes, follow-up

The charter deck: one focused area per session with a time box, then triage before the energy is gone.
